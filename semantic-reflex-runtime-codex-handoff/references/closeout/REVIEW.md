## 4. 三处必须显式处理的正文

**F-DOC1：设计批准与实际验证混成同一个状态。** §17.5 写“没有用户逐项评审、真实接入和实验结果，不能标 Accepted 或 Verified”，容易使设计永远不能收束。[M17，L40–42](evidence/M17.txt) PATCH-01 将设计 Draft/Reviewed/Accepted 与对象级 Verified 分开；接受通用合同不自动接受具体宿主，更不代表收益成立。

**F-DOC2：首发范围摘要错误。** §16.11 写“四能力首发范围不变”，与 CURRENT、§16.0 和 §17.1 不一致。[M16，L90–96](evidence/M16.txt) PATCH-02 改为“四能力长期版图不变；首发仅单类 ADMIT＋recall”。CHANGELOG 同样的旧措辞留作历史并在本包显式注明，不能作为现行范围依据。

**F-DOC3：旧回退摘要可能绕过保留约束。** §05.7 笼统写“结构关联未知或组超预算时回基线”。[M05，L45–51](evidence/M05.txt) §06.11 则区分事件无效、块级弃权和保护闭包溢出。[M06，L84–99](evidence/M06.txt) PATCH-03 明确引用该主规则，防止将保护溢出误映射到仍会延后该证据的 B。这是文档风险，不声称已经发现真实运行事故。

三处替换文本和可核对 diff 在 [PATCHES](PATCHES.md)／[补丁](proposed-closeout.patch)。**修订已用于本包的合并候选阅读稿；原 v0.6 档案未修改、未假称已批准。**

## 5. 现在应冻结什么，保留什么开放？

建议冻结：首发边界、责任和权力划分、source/view/K/D/H 语义、保护优先与回退规则、直接召回及保留义务、有限提交状态、证据/实验分流，以及可否决项目的评测口径。集中见 [首发逻辑基线](BASELINE.md)。

不再深化：DISCLOSE、完整 EXPAND、OBSERVE、review/completion、摘要、多宿主总线、Registry、在线学习和商业平台。保留明确的重新开启条件，不把后置当未来必做承诺。[M17，L9–38](evidence/M17.txt)

## 8. 如何真正结束，而不是再做无限评审？

**文档收束出口：** 项目负责人批准本包范围、G1–G5 和三处修订，实施者按场景追踪复述关键路径；若没有登记在案的逻辑冲突，就冻结该宿主无关基线。若仍有冲突，只修改明确受影响条款，不重新组织全书。

**首发整体架构出口：** F1–F3 在选定宿主上关闭、生产映射和支持范围被评审，才能说该宿主可实施架构完成。原计划的未知接入点禁跳过规则仍生效。

**部署出口：** 依原 E1–E5 证明实际可用与净收益，另外批准启用。书写完成、文审完成、设计批准都不能代替这个出口。

若目前拿不到宿主源码/文档/trace，则暂停该验证范围，不再续写“完整 Runtime 应有的功能”，不为等待凭空设定技术栈。

冻结后仅以下情况重开受影响合同：明确范围变更；真实宿主事实与假设冲突；可复验反例暴露现行合同缺口；跨章矛盾导致两种不兼容实现。仅增加样本、修复不改变合同的代码 bug、调已授权参数或更新账单，分别进入实验/实现记录，不升级整本架构。
